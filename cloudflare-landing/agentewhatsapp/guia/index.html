legalops.dev / build 001 / guia

entenda cada peça enquanto constrói.

Este guia acompanha o build 001 do primeiro webhook ao piloto. A ideia é que você saiba por que cada camada existe, o que ela faz e como adaptar o mesmo raciocínio para outros produtos jurídicos.

canalWhatsApp / Uazapi
dadosSupabase
backendWebhook / deploy
IAprovider + limites

01 / PROTOTIPAR

faça o menor sistema que prova a ideia.

Separe canal, dados, regras, contexto e resposta. Isso deixa o projeto mais fácil de entender, testar e trocar de ferramenta depois.

01

WhatsApp / Uazapi

Conecte a instância e trate o WhatsApp apenas como entrada e saída.

atenção: sessão, credenciais e duplicidade precisam ser observáveis.
02

Supabase

Modele solicitantes, conversas, mensagens, status e contexto em estruturas separadas.

atenção: limite acesso e retenção desde o início.
03

Provider de IA

Dê ao modelo tarefas delimitadas, como classificar, extrair, resumir ou preparar um rascunho.

atenção: defina contexto permitido, custo, fallback e revisão humana.
04

Webhook

Conecte entrada, contexto, regras, modelo e resposta em uma camada que você consegue depurar.

atenção: trate estado, duplicidade, loops e retries.

02 / OPERAR

publique sem perder a capacidade de explicar o sistema.

Quando o protótipo funciona, adicione infraestrutura, acesso, logs, recuperação e critérios claros para intervenção humana.

05

Infraestrutura

Hospede o backend com domínio, HTTPS, processo de aplicação e rotina de backup.

atenção: segredos, dependências e recuperação precisam estar documentados.
06

Acesso

Use acessos separados, menor privilégio e credenciais fora de código e histórico.

atenção: evite contas e tokens compartilhados.
07

Deploy e logs

Acompanhe processo, erros, integrações e sinais mínimos de saúde do fluxo.

atenção: não copie conteúdo jurídico sensível para logs sem necessidade.
08

Governança

Defina tarefas permitidas, dados usados, retenção, revisão e critérios de transferência para uma pessoa.

atenção: confidencialidade e decisões relevantes exigem controles proporcionais.

03 / CHECKLIST

o mínimo antes de colocar o build nas mãos de alguém.

01tokens, chaves e credenciais fora do código e separados por ambiente
02acesso ao banco limitado ao que cada serviço e pessoa realmente precisam
03webhook com validação, estado, idempotência e retry limitado
04logs suficientes para investigar falhas sem copiar conteúdo sensível desnecessariamente
05tarefas permitidas para a IA, limites de custo, fallback e revisão definidos
06piloto pequeno, casos de teste e caminho claro para atendimento humano

PRINCÍPIO DO BUILD

se você consegue explicar o sistema, você consegue melhorar o sistema.

Construir aqui não é decorar ferramentas. É entender como as partes se conectam até você conseguir adaptar o projeto para outro problema jurídico.
